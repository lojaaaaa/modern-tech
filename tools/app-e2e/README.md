# Проверка целого приложения в браузере

Стенд использует настоящие API, PostgreSQL, Redis, серверные cookie-сессии,
CSRF и локальную доставку писем в Mailpit. Это отдельный Docker Compose project
`modern-tech-app-e2e`; рабочие БД, Redis, документы и письма основной инсталляции
в него не подключаются. Неопубликованные Office-прототипы здесь не подменяются.

Образы `modern-tech-api:local`, `postgres:18-alpine`, `redis:7.4-alpine`,
`nginx:1.28-alpine`, `axllent/mailpit:v1.27` и закреплённый в Compose Node24
должны быть подготовлены локально. Backend vendor должен соответствовать
`composer.lock`. При первом запуске пустого frontend-кэша требуется интернет
для `npm ci`; при изменении lockfile повторите установку в отдельном web volume.

Из корня репозитория:

```sh
bash tools/app-e2e/start.sh
npm --prefix tools/app-e2e ci --ignore-scripts
```

Приложение: `http://localhost:8892`, Mailpit: `http://localhost:8893`.
Публичные порты привязаны к loopback. Файл `.local/app-e2e/backend.env` создаётся
из `.env.example` с отдельными ключом приложения, именем cookie и случайным
паролем отдельной БД; реальная `.env` не копируется. Секреты и отчёты находятся
только в игнорируемом `.local/app-e2e/`.

Для рабочей копии задачи можно явно выбрать исходники и постоянное место
состояния, сохранив БД при последующем переключении к следующей задаче:

```sh
bash /path/to/worktree/tools/app-e2e/start.sh /path/to/worktree /path/to/main/.local/app-e2e
```

Запускается только `migrate`, без сброса БД и удаления файлов. Письма попадают
в отдельный Mailpit через SMTP. `QUEUE_CONNECTION=sync` позволяет наблюдать
отложенные до commit уведомления без worker; реальная доставка внешнему
почтовому провайдеру этим не проверяется.

PHP development server запускается с четырьмя Linux worker-процессами и
`--no-reload`, чтобы проверки параллельных HTTP-запросов действительно могли
пересекаться. Это тестовая среда, не конфигурация production-сервера.

Остановка с сохранением данных:

```sh
docker compose -f tools/app-e2e/compose.yaml --env-file .local/app-e2e/compose.env down
```

Браузерные сценарии сохраняют отчёт о фактических шагах и screenshots/traces
в игнорируемое место. Signed URL и токены писем не публикуются в итоговом отчёте.

Проверка регистрации и подтверждения email:

```sh
node tools/app-e2e/registration.mjs
node tools/app-e2e/session.mjs
```

`E2E_URL` и `E2E_MAILPIT_URL` меняют адреса приложения и отдельного Mailpit,
`E2E_REPORT_DIR` — каталог отчётов, `CHROME_PATH` — путь к Chrome. Сценарий создаёт
свой уникальный тестовый аккаунт, не очищает чужие письма и не сбрасывает БД.
Проверяются настоящая SMTP-доставка, CSRF, запрет загрузки до подтверждения и
приём файла после перехода по полученной ссылке.

`session.mjs` проверяет последовательные входы с приватным документом и тестовым
облачным подключением, восстановление пароля по настоящему письму и блокировку
открытой сессии. Для блокировки он повышает созданного сценарием пользователя
до администратора через `docker exec` только в отдельном контейнере
`modern-tech-app-e2e-api-1`; поэтому требуется Docker и адрес по умолчанию
`http://localhost:8892`. На основной базе этот сценарий запускать нельзя.
Открытые редакторские соединения этим сценарием не проверяются.
