# Дизайн и руководство для фронтенда

Основание: согласованный [SPEC.md](SPEC.md), навык `frontend-design` и
[исследование 48 материалов](research/README.md). Продуктовый объём определяет
SPEC; точные строки определяет [COPY.md](COPY.md).

## Дизайн-направление

Личный архив для пользователя Telegram. Главная задача экрана — найти
собеседника и понять событие переписки. Визуальный язык — знакомый Telegram,
сдержанная плотность и ясная история версий.

Применение `frontend-design` здесь не означает новую брендированную палитру,
декоративную гарнитуру или необычную навигацию. Бриф прямо выбрал Telegram;
он важнее общих советов навыка об оригинальности. Индивидуальное качество
проекта — точное представление правок, недоступных данных и прочтения.

Рассмотрены два направления:

```text
Выбрано: диалоги → события → история
[Поиск]
[Аватар Имя     Время]
[Событие          3]   →   [Было / Стало]   →   [Все версии]

Отклонено: универсальная dashboard-композиция
[Сохранено] [Удалено] [Изменено]
[Декоративный обзор]
[Карточки диалогов]
```

Второе направление расходует первый экран на обзор, которого не требует
пользователь. Это наш контекстный выбор, а не запрет dashboard-дизайна вообще.

## Цвета и тема

Основной источник — ThemeParams Telegram; смена темы применяется без перезагрузки.
Не фиксировать светлый макет и не получать тёмный простым инвертированием.
В обычном Telegram WebView не рисовать ещё одну имитацию системной шапки
или статуса устройства. Основание: [Telegram Mini Apps](https://core.telegram.org/bots/webapps),
[Apple Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode).

| Роль приложения | Роль Telegram | Назначение |
| --- | --- | --- |
| background | `bg_color` | Основной фон |
| secondary | `secondary_bg_color` | Фон вторичной области/настроек |
| section | `section_bg_color`, при отсутствии — background | Поверхность групп |
| text | `text_color` | Имя, текст сообщения, название действия |
| secondary-text | `subtitle_text_color` / `hint_color` | Время, пояснение, тип события |
| action | `button_color` и `button_text_color` | Основное действие и его подпись |
| link | `link_color` | Username и текстовые переходы |
| destructive | `destructive_text_color` | Подтверждённое разрушительное действие |

Fallback нужен для локального макета и старого клиента, а не для замены темы.
Предлагаемая светлая базовая палитра из шести цветов:

| Название | Значение |
| --- | --- |
| Белая поверхность | `#FFFFFF` |
| Вторичный фон | `#F2F3F5` |
| Основной текст | `#1C1E21` |
| Вторичный текст | `#596675` |
| Действие | `#1E70B5` |
| Разрушительное действие | `#B32D33` |

Это наши preview-значения, не заявленные официальные hex-цвета Telegram.
С белым фоном расчётный контраст четырёх текстовых цветов составляет примерно
16.71, 5.86, 5.20 и 6.29 соответственно. Эти пары проверены вычислением;
контраст ещё не созданного интерфейса целиком не проверен.

В тёмной теме использовать отдельные семантические роли среды. Вторичный текст,
счётчики, выделение правок и фокус проверять отдельно. Если системная роль
сливается с нашей поверхностью, исправить именно пару, не объявлять всё
приложение доступным из-за наследования темы.

## Типографика, размеры и плотность

Одна системная гарнитура с двумя основными ролями — заголовки и содержимое;
время/подписи используют ту же семью. Это намеренный выбор для сходства
с Telegram, а не случайный шрифтовой дефолт.

Предлагаемая отправная шкала, которую нужно проверить на прототипе:

| Роль | Размер / интерлиньяж | Насыщенность |
| --- | --- | --- |
| Название экрана | 20 / 26 CSS px | 600 |
| Имя собеседника | 16 / 22 CSS px | 600 |
| Текст события и настройки | 16 / 23 CSS px | 400 |
| Предпросмотр, пояснение | 14 / 20 CSS px | 400 |
| Время и метаданные | 13 / 18 CSS px | 400 |

Размеры оформить масштабируемыми единицами. Увеличение текста перестраивает
строку, а не обрезает её фиксированной высотой. `system-ui` не является
доказательством поддержки Dynamic Type в конкретном WebView.
Основание: [Apple Typography](https://developer.apple.com/design/human-interface-guidelines/typography).

Ритм: 4, 8, 12, 16, 24, 32 CSS px. Исходные предложения: поля экрана 16,
аватар 48, расстояние до текста 12; строка диалога имеет минимум около 76,
но растёт с текстом. Иконка около 20–24 при hit area около 44 CSS px.
Эти числа — отправная геометрия проекта, не точная копия всех клиентов Telegram.

Скругления обозначают объект: аватар круглый, сообщение около 12 px,
поле поиска около 10, счётчик — капсула. Не оборачивать каждую строку
в отдельную приподнятую карточку. Разделитель достаточно вести по текстовой
области, если группировка остаётся понятной. Тени нужны для наложенных меню,
а не для каждого сообщения.

## Навигация и компоненты

### Список диалогов

Порядок внимания: имя → последнее событие → непрочитанное → время.
Аватар помогает узнаванию, но не заменяет текст. Пользователь должен отличать
строку диалога, поисковый результат и служебную ошибку.

Строка открывается целиком. Копирование ника — отдельное явное действие
в деталях; оно не должно неожиданно открывать/закрывать диалог.
Непрочитанное обозначается числом и насыщенностью имени, не только цветом.
Для выбранной строки в двух колонках используется отдельное спокойное состояние.

Поиск имеет видимую подпись/доступное имя. Placeholder не является единственной
меткой. При ошибке запроса сохранённый список не исчезает как якобы пустой.
Поиск с опечаткой объясняется результатом, а не рекламой «умного поиска».

### Диалог

Хронологическая лента с датами и сообщениями. У записи виден тип события.
Новое состояние не прячется за обязательным переходом в историю.
Служебные подписи не должны занимать больше внимания, чем изменённый текст.

Пара «Было / Стало» находится внутри одного смыслового блока. Различия
можно подсветить по словам, но подписи сохраняются: красно-зелёный цвет
не является единственным объяснением. Для сложного изменения допустим
полный текст без агрессивного diff. Это предложенный способ подачи,
не новая функция изменения исходной переписки.

У открытия истории должен быть обнаружимый признак: краткая подпись/стрелка
и доступное действие «История сообщения», а не только скрытое знание о тапе.
Копирование/выделение текста не должно случайно открывать историю.
Основание: [NN/g о признаках действия](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/).

При подгрузке и загрузке фото сохраняется читаемый якорь. Задавать размеры
изображения до загрузки, чтобы строка не прыгала. Новое событие не вырывает
из старой правки; доступен явный переход к новым данным. Возврат из истории
восстанавливает место. Основание: [сохранение позиции](https://www.nngroup.com/articles/saving-scroll-position/),
[разбор прокрутки Telegram](https://bureau.ru/soviet/20241105/).

### История

Отдельное представление одного сообщения: исходное полученное состояние,
правки по порядку, времена и удаление, если оно известно.
Пропущенная версия — объяснение отсутствия, а не вымышленный пузырь сообщения.
Не смешивать время оригинала, изменения и время получения ботом.

BackButton оболочки и видимый возврат согласованы с одним navigation state.
Не показывать две конкурирующие кнопки «Назад». На широком экране допустима
панель деталей, если возврат, фокус и исходная позиция остаются предсказуемыми.

### Фото

Карточка сообщает фактическое состояние. Фото неизвестного режима подписано
«Фото», а не «Одноразовое». Полноэкранный просмотр доступен для сохранённого
изображения. Ошибка относится к конкретному файлу и остаётся видимой после тоста.
Иллюстрации, сгенерированные аватарки и стоковые фотографии не подменяют
реальные архивные данные. Для макетов использовать явно вымышленные примеры.

### Настройки и подтверждения

Видны три разных действия: уведомлять, сохранять новые данные, удалить старые.
Названия и пояснения не позволяют перепутать одно с другим. Общие и диалоговые
переключатели связаны по правилам SPEC; локальное включение не обходится
с глобальным выключением.

Подтверждение очистки называет объём и судьбу оригиналов Telegram.
Разрушительное действие названо глаголом с объектом, рядом доступна отмена.
Копирование ника и обычный успех не требуют блокирующего alert.
Основание: [Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts).

## Доступность и Telegram WebView

Это критерии проверки, не заявление о сертификации:

- Обычный текст — контраст 4.5:1, крупный по определению WCAG — 3:1;
  значимые нетекстовые признаки — 3:1 с применимыми исключениями.
- Минимум WCAG AA для pointer target — 24×24 CSS px либо исключение.
  Для частых действий наша цель около 44 CSS px; это не универсальный минимум AA.
- Проверка на 320 CSS px, при увеличении текста и длинных русских сообщениях.
- Семантические кнопки и поля, доступные имена, видимый фокус и порядок Tab.
- Меню/диалог возвращают фокус к вызвавшему элементу. Плавающее «Прочитать всё»
  не закрывает событие и сфокусированное действие.
- Результаты поиска и копирования объявляются подходящими статусами без
  перехвата фокуса. Не делать всю историю непрерывным `aria-live`-потоком.
- Различать viewport height и stable height, safe area и content safe area;
  учитывать поддержку конкретного клиента и fallback.
- Смена темы, открытие клавиатуры и изменение размера окна не теряют состояние.

Нормативные различия и первичные ссылки: [P06–P13](research/platform-and-accessibility.md).
Нативные Apple `pt`, CSS px и физические пиксели не взаимозаменяемы.

## Проверка против шаблонной AI-подачи

Рубрика оценивает результат, а не устанавливает авторство:

| Проверка | Признак проблемы в нашем приложении |
| --- | --- |
| Назначение каждого элемента | Метрики, слоган, декоративный hero или навигация без задачи владельца |
| Иерархия | Время и служебный badge громче имени или самой правки |
| Смысл границ | Карточки внутри карточек без разных объектов/уровней |
| Узнаваемость | Необычное действие вместо привычного Telegram без выигрыша |
| Истинность | «Сохранено» при отсутствии полного файла, активный сбор без связи |
| Состояния | Один тост на пустой архив, сетевую ошибку и недоступное фото |
| Кликабельность | Историю нельзя найти без подсказки автора |
| Плотность | Чрезмерный воздух вытеснил содержание; уплотнение сделало текст нечитаемым |
| Текст | Обещания, канцелярит и повтор заголовка вместо состояния/действия |

Градиент или карточка сами по себе не проваливают проверку. Причина изменения
должна ссылаться на задачу, состояние или доступность, а не на «так не похоже на ИИ».

## Приёмка дизайна

Сначала проверяются задачи SPEC: найти собеседника с опечаткой, прочитать
изменение отрицания/времени, открыть историю, вернуться без потери места,
различить статусы фото, отключить уведомления без остановки сбора, очистить
нужный объём и сохранить корректный счётчик.

Набор данных: длинное имя и username, отсутствие аватарки, много правок,
большой текст, emoji, несколько событий с одинаковым временем, удалённый
оригинал, яркое фото, отсутствие сети, пустой результат поиска.

Проверить узкое/широкое окно, обе темы, увеличение текста, клавиатуру,
screen reader, reduced motion и safe areas. Снять скриншоты одинаковых
состояний для сравнения; отдельно выполнить задачи и записать ошибки.
Не объявлять удобство доказанным только после self-review моделью.
Подробный протокол: [исследование UX](research/ux-quality-and-visual-patterns.md).
