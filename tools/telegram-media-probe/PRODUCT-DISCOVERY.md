# Проработка продукта Telegram-архива

Обновлено: 2026-11-09. Статус: интервью завершено; итоговый объём подтверждён
пользователем. Действующая спецификация: [SPEC.md](SPEC.md), версия 1.0.
Здесь сохранён ход обсуждения; поздние уточнения заменяют ранние предложения.

## Исходные требования

- Главный приоритет пользователя: сохранять одноразовые медиа и сообщения с таймером.
- Показывать уведомления об изменении и удалении сообщений.
- Дать удобный интерфейс просмотра архива.

## Наблюдения прототипа

- В тестовом бизнес-чате обычное фото было получено и скачано.
- Два одноразовых фото не пришли как самостоятельные сообщения.
- После ответов на них одно событие содержало фото в `reply_to_message`.
  Из него скачан JPEG 960×1280. Другой ответ содержал только метаданные.
- Эти наблюдения не подтверждают автоматическое сохранение всех одноразовых
  медиа, видео или работу после исчезновения оригинала.
- Предыдущий запущенный вариант поддерживал просмотр последних пяти фото
  владельцем через `/photos` и кнопку в боте.
- Очередь уведомлений и индекс версий начали добавлять в код, но изменения
  ещё не проверены и не запущены. Готовой функцией их не считаем.

## Согласовано: раунд 1

- Первая версия — личный инструмент. Подписки рассматриваются в будущем,
  в текущую версию не входят.
- Автоматическое сохранение временных медиа остаётся желаемым результатом.
  Ручной сценарий допустим, если надёжного автоматического варианта нет.
  Ни один вариант не обещаем для всех типов до воспроизводимой проверки.
- Видимый архив содержит события и самоуничтожающиеся фото, а не полную
  историю обычных сообщений.
- Основной экран — список диалогов по собеседникам, как в Telegram.
- В диалогах нужны имена, usernames и аватарки собеседников, когда Telegram
  предоставляет эти данные. Правило обновления профиля пока не выбрано.
- Диалоги с непрочитанными событиями выделяются и показывают их количество.

## Согласовано: раунд 2

- Интерфейс — полноценный Telegram Mini App с визуальным языком самого
  Telegram. Пользователь не выбрал отдельный авторский стиль для приложения.
- В архив входят собственные изменения/удаления и действия собеседника.
  Уведомления отправляются только о действиях собеседника.
- Событие становится прочитанным только после показа на экране.
  Нужна кнопка «Прочитать всё». Уведомление бота не обнуляет счётчик.
- Базовый режим — немедленные уведомления об изменениях и удалениях;
  пользователь может их настраивать. Детали настроек ещё обсуждаются.
- Диалоги сортируются по последнему событию.
- Фоновые копии обычных сообщений хранятся 30 дней. События и сохранённые
  фото — до ручного удаления. Для удаления более старого сообщения
  сохранённого содержимого может не оказаться.
- [ADR: сроки хранения](../../docs/adr/0006-telegram-archive-retention.md).

## Согласовано: раунд 3

- Собственные изменения/удаления не увеличивают счётчик непрочитанных.
- Пользователь повторно подтвердил сохранение только самоуничтожающихся фото
  и приоритет автоматического сценария. Конкретная ручная команда не выбрана;
  предложенная `.save` не считается согласованной.
- Сохраняются все полученные промежуточные правки сообщения.
  Нажатие на сообщение открывает его историю.
- Настройки уведомлений имеют два уровня: общие переключатели изменений
  и удалений и отключение уведомлений отдельного диалога. Архивирование
  и счётчик непрочитанных продолжают работать при выключенных уведомлениях.
- Текущая версия работает на Mac. Постоянный сервер — последующий этап,
  а не требование текущего запуска.

## Согласовано: раунд 4

- Для удалённого обычного медиа показываются факт удаления, тип и подпись,
  без постоянного сохранения самого файла. Для текста — сохранённый текст.
- В первой версии поиск только по имени и username собеседника,
  с допуском к опечаткам. Поиск по содержимому не включён.
- Можно удалить отдельную запись, очистить диалог и весь архив, с подтверждением.
- Очистка не меняет оригинальную переписку и удаляет сохранённые события,
  фото и фоновые копии соответствующего объёма. Новые события после очистки
  могут появляться снова.
- Для прекращения сбора есть отдельная настройка «Не сохранять этот диалог».

## Гипотезы, а не решения

- «След» — лишь ранее предложенное рабочее название; пользователь его
  не утверждал. Ранее предложенная самостоятельная палитра не применяется:
  согласовано визуальное соответствие Telegram.
- Дополнительные фильтры событий и непрочитанных не входят в явно выбранный
  объём первой версии. Пользователь ограничил обсуждённый поиск именем/username.

## Подтверждённые ограничения

- Для показа удалённого содержимого нужна заранее полученная копия: событие
  удаления содержит только идентификаторы. «Только события в интерфейсе»
  не означает отсутствие промежуточного хранения обычных сообщений.
- API Terms §1.4 запрещает сторонним клиентам препятствовать исчезновению
  самоуничтожающегося контента; MTProto не считаем автоматически разрешённым
  обходом. Это положение само по себе не запрещает любой архив обычных
  сообщений через бизнес-бота.
- Bot Developer Terms §5.4 допускает хранение при раскрытии состава, срока
  и цели; также применяются требования к удалению и защите данных.

Источники: [BusinessMessagesDeleted](https://core.telegram.org/bots/api#businessmessagesdeleted),
[API Terms](https://core.telegram.org/api/terms#1-privacy-security),
[Business Bot Terms](https://telegram.org/tos/bot-developers#5-4-telegram-business).

## Расхождения с текущим прототипом

- Приёмник скачивает обычные фото, а не только выбранные временные медиа.
- В незапущенном коде уведомлений пока нет фильтра собственных действий.
- Очистка по сроку, Mini App и состояние прочтения ещё не реализованы.

## Результат технической проверки фото

В официальном исходнике HTTP Bot API самоуничтожающиеся сообщения
намеренно исключаются из новых обновлений, включая бизнес-очередь.
Проверена версия e3e9dd8e5b3d7ab8537cd5a10dc31d5ffa8f82d1; точная версия
облачного сервера неизвестна. Наблюдаемое отсутствие прямых обновлений
согласуется с этой реализацией.

- [Флаг самоуничтожения](https://github.com/tdlib/telegram-bot-api/blob/e3e9dd8e5b3d7ab8537cd5a10dc31d5ffa8f82d1/telegram-bot-api/Client.cpp#L19632)
- [Исключение из обновлений](https://github.com/tdlib/telegram-bot-api/blob/e3e9dd8e5b3d7ab8537cd5a10dc31d5ffa8f82d1/telegram-bot-api/Client.cpp#L18913)
- [Применение фильтра к бизнес-сообщениям](https://github.com/tdlib/telegram-bot-api/blob/e3e9dd8e5b3d7ab8537cd5a10dc31d5ffa8f82d1/telegram-bot-api/Client.cpp#L19453)

HTTP Message не даёт явного TTL-признака; `has_protected_content` не доказывает
режим «один просмотр». Поэтому получение файла внутри reply не позволяет
гарантировать автоматический отбор только временных фото.

MTProto допускает авторизацию именно бота без входа в личный аккаунт;
его схема выражает `ttl_seconds`. Это не доказывает выдачу конкретного файла,
не гарантирует скачивание и не снимает ограничений условий платформы.

Автосохранение временных фото остаётся отдельным неподтверждённым требованием.
Согласованный ниже компромисс касается только фото из ответов владельца,
а не всех обычных входящих фото. Гарантии получения файла не подтверждены.

## Согласовано: раунд 5

- В списке диалогов — последние доступные данные профиля; в деталях события —
  сведения, известные на момент события. Telegram ID сохраняет идентичность
  диалога при смене имени/username.
- Последнее уточнение пользователя заменяет прежнее краткое согласие Q19:
  триггер — любой ответ владельца на фото, без команды `.save`.
- Собеседнику бот не отправляет отдельного сообщения о сохранении;
  результат виден только владельцу. Незаметность всех действий Telegram
  этим не гарантируется.

## Согласовано: Q20 — компромисс отбора

- При невозможности надёжно различить тип фото разрешено сохранять все
  доступные фото, на которые владелец отвечает, включая обычные.
- Обычные фото без ответа владельца автоматически в постоянный архив
  не попадают. Ответ другого участника не равен ответу владельца.
- Это явное уточнение первоначального требования «только временные фото».
  Неизвестный режим фото не обозначается в интерфейсе как одноразовый.
- Исследование автоматического сохранения без ответа владельца сохраняется
  отдельной задачей и не считается завершённым.

## Подтверждение итогового объёма

Пользователь подтвердил итоговый объём и поручил оформить спецификацию.
Первая версия включает согласованный архив событий, фото по ответу и Mini App.
Автосохранение временных фото без ответа остаётся отдельным исследованием,
без обещания результата. Финальная сверка получена; повторное подтверждение
перед обычной реализацией не требуется.
