# Office collaboration prototype

Изолированный стенд задачи02. Он не подключается к приложению, рабочей БД,
очередям или пользовательским файлам. Проверяемый кандидат: **ONLYOFFICE Docs
Community9.4.0.1**, Linux ARM64. Ни лицензия Developer, ни Automation API не нужны.
Это технический кандидат; итоговый выбор редактора остаётся задачей06.

## Запуск

Из корня репозитория; нужны Docker Compose, Python3.12+ и Node24+. Подготовка
пакетов требует интернета; после загрузки образов/пакетов стенд работает локально.

```sh
python3 -m venv tools/office-poc/.venv
tools/office-poc/.venv/bin/pip install -r tools/office-poc/requirements.txt
tools/office-poc/.venv/bin/python tools/office-poc/corpus.py generate
tools/office-poc/.venv/bin/python tools/office-poc/corpus.py verify
node -e "require('fs').writeFileSync('tools/office-poc/.env','JWT_SECRET='+require('crypto').randomBytes(32).toString('hex')+'\n')"
mkdir -p tools/office-poc/data
docker compose -f tools/office-poc/compose.yaml --env-file tools/office-poc/.env pull
docker compose -f tools/office-poc/compose.yaml --env-file tools/office-poc/.env up -d --wait --wait-timeout 420
```

Имена Compose project/network/volumes содержат `modern-tech-office-poc`. Порты8890
и8891 привязаны к loopback. Секрет, корпус, результаты и кэш игнорируются Git.
Отладочный HTTP-сервис разрешает две фиксированные личности без входа; это
только локальный стенд, а не реализация авторизации платформы. Private-IP fetching
разрешён редактору специально для внутреннего адреса `http://harness:8890`.

Остановка сохраняет результаты и кэш:

```sh
docker compose -f tools/office-poc/compose.yaml --env-file tools/office-poc/.env down
```

## Воспроизводимый корпус

`corpus.py` создаёт три настоящих файла Office Open XML и `manifest.json` с SHA256.
ZIP-метаданные и дата изменения фиксированы. Полученные SHA256 относятся к среде,
указанной в отчёте; версия zlib/зависимостей может влиять на сжатие. Семантическая
проверка важнее одинакового ZIP-потока на разных платформах.

- DOCX: заголовок, Unicode, жирный фрагмент, две одинаковые цитаты, таблица3×2.
- XLSX: два листа, формулы `=B2*2` и `=SUM(A3:B3)`, формат заголовка, ширины,
  закреплённая строка. Исходный файл содержит формулы без вычисленного кэша;
  после редактирования проверяется и вычисленное значение42.
- PPTX: два слайда16:9 с заголовками и Unicode. Порядок слайдов проверяется.

Макросы, SmartArt, диаграммы, вложенные объекты, сложная вёрстка, все шрифты и
побитовая сохранность произвольных файлов этим небольшим корпусом не доказаны.

## Протокол двух клиентов

Для каждого формата открыть две **независимые сессии браузера**. Обычное и
приватное окно допустимы. Идентичный `document.key` на обоих клиентах проверяется
HTTP-тестом; редактор получает разные ID и имена.

| Формат | Алиса | Борис |
|---|---|---|
| DOCX | `http://localhost:8890/?file=sample.docx&user=alice` | `http://localhost:8890/?file=sample.docx&user=bob` |
| XLSX | `http://localhost:8890/?file=sample.xlsx&user=alice` | `http://localhost:8890/?file=sample.xlsx&user=bob` |
| PPTX | `http://localhost:8890/?file=sample.pptx&user=alice` | `http://localhost:8890/?file=sample.pptx&user=bob` |

1. Убедиться, что оба видят второго участника по имени, а при перемещении каретки,
   выделения ячейки или работе со слайдом видна метка/курсор соавтора. Сохранить
   скриншоты обоих окон. Наличие только списка участников не доказывает курсоры.
2. DOCX: Алиса добавляет новый абзац `ALICE_DOCX` в конце документа; Борис видит
   его **без обновления** и добавляет отдельный абзац `BOB_DOCX`. Алиса также видит
   его без обновления. Сохранить результат на обоих клиентах.
3. XLSX: Алиса меняет `Расчёт!A3` на17; Борис видит17, меняет `B3` на25; Алиса
   видит25. `C3` остаётся формулой и показывает42. Проверить исходные форматирование
   и второй лист.
4. PPTX: Алиса дописывает `ALICE_PPTX` в текст первого слайда; Борис видит его и
   дописывает `BOB_PPTX` во второй. Алиса видит обновление второго слайда.
5. Завершить ввод, нажать «Запросить сохранение». Ответ command service сам по
   себе **не означает**, что файл получен. В `http://localhost:8890/events` должен
   появиться callback со статусом6, `bytes` и `sha256` после успешного скачивания.
   До этого сохранение не считать подтверждённым.
6. В обоих окнах нажать «Закрыть редактор». Дождаться статуса2 либо4. Только
   теперь открыть обе ссылки заново; новый session key заставляет редактор
   скачать файл, который действительно получил сервис хранения. Повторить
   проверки текста, ячеек, формул, порядка и содержимого слайдов.
7. Проверить полученные файлы независимо от редактора:

```sh
tools/office-poc/.venv/bin/python tools/office-poc/corpus.py inspect tools/office-poc/data
tools/office-poc/.venv/bin/python tools/office-poc/corpus.py verify tools/office-poc/data --edited
```

`verify --edited` требует файлы всех трёх форматов, оба маркера DOCX/PPTX,
A3=17/B3=25, сохранённые формулы, вычисленный результат42, таблицу, жирный фрагмент
и порядок слайдов. Команда падает при отсутствии хотя бы одного файла/изменения.
Копирование исходных файлов в `data/` не проходит эту проверку.

## Автоматические проверки стенда

HTTP-тесты доказывают общий ключ двух участников и запрет поддельного callback;
они не заменяют редактор.

```sh
docker run --rm --network none -v "$PWD/tools/office-poc:/poc" -w /poc node:24-alpine@sha256:f70403e87646dc51b45295f4b8b70cdad0b63d2297c4c9899119b03f7af7a6b3 node --test tests/http.test.mjs
npm --prefix tools/office-poc ci --ignore-scripts
node tools/office-poc/browser.mjs
```

`browser.mjs` открывает все три формата двумя независимыми контекстами Chrome,
сохраняет screenshots/DOM и `data/browser/readiness.json`. `CHROME_PATH` задаёт
путь к Chrome, если он отличается от macOS-пути по умолчанию. Это **readiness
probe**; автоматический ввод, курсоры, согласованность и повторное открытие
не объявляются проверенными на основании одного `onDocumentReady`.

HTTP-сервис проверяет HS256 callback, session key, допустимый хост и `/cache/`,
скачивает файл без перенаправлений и атомарно меняет локальный файл. Он не
реализует согласованную границу файла и обсуждений, дедупликацию поздних callback,
отзыв прав или места10/11 — это отдельные задачи03–06. Состояние из callback
отделено в UI от загрузки редактора и от приёма ввода.

Фактические результаты и источники: [отчёт](../../docs/research/office-poc-results.md).

## Настоящий контур двух клиентов

`acceptance.mjs` дополняет readiness probe полным сценарием. Он использует
**бесплатный тестовый плагин** внутри настоящего редактора: документированные
`Asc.plugin.callCommand` и Office JavaScript API читают и меняют исходное
содержимое. `createConnector()` и платный Automation API не используются.
Плагин включается только при `validation=1`; обычный запуск его не загружает.

```sh
POC_PYTHON=tools/office-poc/.venv/bin/python node tools/office-poc/acceptance.mjs
```

Код выхода0 означает прохождение запрошенного контура; код1 — ошибку или
неподтверждённый обязательный критерий. При запуске без аргументов результат
`passed` требует все три формата и независимую проверку файлов.

Если venv находится вне репозитория, `POC_PYTHON` задаёт его абсолютный путь.
Можно передать `docx`, `xlsx` или `pptx` для диагностики выбранного формата;
частичный запуск не является приёмкой всех трёх форматов.

Для каждого формата сценарий открывает два независимых контекста, проверяет
один session key и разные личности, вносит изменения Алисы и Бориса и ждёт их
сходимости без обновления страниц. DOCX/PPTX используют уникальные маркеры
текущего запуска. XLSX сначала меняется на10/20 через реальный редактор с
подтверждением обоих клиентов, затем на17/25 с результатом формулы42.

Проверка курсоров требует видимой нативной метки `.username-tip[userid]`
ожидаемого соавтора внутри области документа; наличие имени в списке участников
или подсказке заблокированного объекта не считается успехом. У закреплённой
версии эти типы меток различаются атрибутом `userid`. Проверяются оба
наблюдателя, а неуспешный PPTX дополнительно записывает диагностику наведения
на объект; такая подсказка сама по себе не является курсором. При обновлении
редактора DOM-селектор необходимо подтвердить заново.

После редактирования принимается только новый callback6 текущего key с
временем не раньше запроса сохранения, размером и SHA256 скачанного файла.
Затем оба клиента закрываются; новый запуск обязан получить другой key и
заново открыть сохранённое содержимое. После трёх форматов Python независимо
проверяет скачанные файлы через `corpus.py verify --edited`. Полный результат
`passed` возможен только при успешных живых проверках и проверке всех файлов.

Результаты каждой попытки сохраняются отдельно в `data/acceptance/<timestamp>/`:
отчёт, screenshot, DOM, Playwright trace, реальные файлы callback и результат
Python. Предыдущие артефакты не удаляются; старые файлы/события не заменяют
доказательства текущей попытки.

курсоров или повторного открытия этим запуском не объявляется пройденной.

Первичные API: [runtime plugins](https://api.onlyoffice.com/docs/docs-api/usage-api/config/editor/plugins),
[бесплатные команды плагина до10.0](https://api.onlyoffice.com/docs/plugins/interacting-with-editors/overview/how-to-call-commands),

## Экспериментальная панель обсуждений

Добавьте `&discussion=1` к одной из ссылок выше, например
`http://localhost:8890/?file=sample.docx&user=alice&discussion=1`. Откройте
такую же ссылку с `user=bob` в другом профиле. Выделите содержимое в редакторе,
введите замечание в панели приложения. Плагин создаёт нативный комментарий в
текущем выделении; панель отображает тот же список из `GetAllComments`, включая
ответы, созданные в редакторе. В DOCX кнопка перехода вызывает `MoveToComment`.
Для XLSX и PPTX переход пока не предоставляется.

Форма ответа в панели перед записью перечитывает нативную ветку и передаёт её
в `ChangeComment`, после чего ищет ответ в новом списке редактора. Набранный
текст сохраняется при обновлении панели; автоматический повтор при тайм-ауте
не выполняется. Плагин упорядочивает запросы одного клиента, но **не может
атомарно согласовать параллельные изменения разных клиентов**: `ChangeComment`
заменяет данные ветки целиком, поэтому одновременный ответ в другом окне может
быть перезаписан даже после локального подтверждения. Прототип не обеспечивает
надёжное сохранение ответов и не предназначен для пользовательских данных.
Метод описан в [API ONLYOFFICE](https://api.onlyoffice.com/docs/plugins/interacting-with-editors/document-api/Methods/ChangeComment).
На проверенном DOCX редактор возвращает ответ без `UserId`; подтверждение
сопоставляет имя, время и текст, которые не образуют надёжный уникальный ключ.
Один живой сценарий подтвердил показ ответа второму клиенту в текущей сессии;
поведение XLSX/PPTX, конкурентные ответы и полное повторное открытие не проверены.

Панель и плагин обмениваются сообщениями только в рамках происхождения стенда.
Участники и документы фиксированы синтетическим harness; это не авторизация и
не защищённый междоменный протокол приложения. Нативный ID — временная связь с
веткой в текущей сессии; его постоянство при полном закрытии и повторном открытии
ещё не доказано. Цвет вычисляется из пары имени тестового файла и ID автора;
для исходных комментариев без ID используется имя. Цвет офисного курсора другой.

При запуске и возвращении фокуса выполняется полное перечисление, а затем оно
повторяется каждые пять секунд. DOCX-события дополнительно запрашивают новое
перечисление: события здесь только подсказки, их порядок и доставка не считаются
гарантированными. Ошибка перечисления сохраняет последнее отображение с сообщением
об ошибке, но не доказывает удаление ветки или привязки. При закрытии редактора
панель очищается. Если плагин не отвечает, страницу требуется перезагрузить.

Сохранение утраченной привязки и цитаты, безопасное определение удаления,
снимки опубликованных версий, права доступа, надёжность доставки, конкурирующие
ответы, а также сохранность ID/привязок при изменении структуры и повторном
открытии ещё не реализованы или не подтверждены. По совпадению текста привязка
не восстанавливается. Это прототип задачи03, не реализация ADR-005.
