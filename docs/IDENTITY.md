# Регистрация и подтверждение электронной почты

Посетитель создаёт аккаунт сотрудника через `/register`. Регистрация не принимает
роль администратора и не подтверждает email из пользовательского payload. Адрес
нормализуется в нижний регистр; повтор существующего адреса отклоняется.

После регистрации пользователь входит в серверную cookie-сессию и видит следующий
шаг на `/verify-email`. До подтверждения можно входить и читать доступные документы.
Загрузка, импорт, изменение документов и добавление/изменение комментариев запрещены
сервером, включая повторную проверку в обработчике импорта. UI объясняет ограничение
и позволяет повторно запросить письмо.

Ссылка из письма подписана, действует 60 минут и подтверждает только аккаунт,
который сейчас вошёл в приложение. Изменённая, просроченная или чужая ссылка
отклоняется. Повтор действительной ссылки не меняет время подтверждения.
Регистрация ограничена пятью запросами в минуту на IP, повторная отправка — шестью
запросами в минуту на аккаунт; ответы 429 содержат `Retry-After`.

Существующим, демо- и созданным администратором аккаунтам подтверждение не
присваивается автоматически. Если `email_verified_at` пуст, пользователь входит
и запрашивает письмо на `/verify-email`. Тестовая фабрика по умолчанию создаёт
подтверждённых пользователей; состояние `unverified()` проверяет ограничения.

## Почта и запуск

Локальная конфигурация использует SMTP Mailpit: `MAIL_MAILER=smtp`,
`MAIL_HOST=mailpit`, `MAIL_PORT=1025`, `MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME`.
`APP_URL` должен совпадать с адресом приложения в браузере: он входит в подписанную
ссылку. В основной Compose-инсталляции Mailpit доступен на `localhost:8026`,
в отдельном браузерном стенде — `localhost:8893`.

Уведомления подтверждения выполняются после commit в очереди `short`. При
`QUEUE_CONNECTION=redis` необходим worker, например существующий сервис `worker`
с очередями `short,default`. После обновления кода перезапустите долгоживущие
worker-процессы (`php artisan queue:restart` и штатный перезапуск сервиса).
В изолированном браузерном стенде используется `QUEUE_CONNECTION=sync`, чтобы
наблюдать SMTP-доставку без отдельного worker.

Для реальной отправки настройте свой SMTP-транспорт через `MAIL_HOST`, `MAIL_PORT`,
`MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SCHEME` и адрес отправителя. Секреты
остаются в `.env`, не в Git. Доставка внешнему провайдеру в этой задаче не проверялась;
подтверждена только настоящая локальная доставка через отдельный Mailpit.

## Проверки

HTTP feature-тесты: `backend/tests/Feature/RegistrationTest.php`.
Полный браузерный сценарий с настоящими PostgreSQL, Redis, cookie/CSRF и Mailpit:

```sh
bash tools/app-e2e/start.sh
node tools/app-e2e/registration.mjs
```

Сценарий проверяет запрет без CSRF, регистрацию сотрудника, состояние до
подтверждения, исходное и повторное письмо, реальную ссылку, идемпотентное
подтверждение и приём загрузки после проверки адреса. Обработка загруженного файла
не объявляется пройденной этим сценарием. Отчёты и trace содержат только локальные
тестовые данные и находятся в игнорируемом `.local/app-e2e/reports/`.

OpenAPI экспортируется Scramble; клиентские типы генерируются из него:

```sh
cd backend
php artisan scramble:export --path=../contracts/openapi.json
cd ../frontend
npm run generate:api
```

Новые операции — `POST /api/v1/auth/register`,
`POST /api/v1/auth/verification-notification`,
`GET /api/v1/auth/verify-email/{id}/{hash}?expires=…&signature=…`.
Экспорт документирует общий envelope ошибок, фактически возвращаемый API.
