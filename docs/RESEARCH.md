# Исследование архитектуры и продукта

> Обновление 31.10.2026: владелец согласовал пакет решений. Текущая нормативная baseline - [SPECIFICATION.md](SPECIFICATION.md). Ниже сохраняется история исследования; старые открытые вопросы не отменяют принятую спецификацию.

Дата проверки источников: 2026-10-31. Статус: первая итерация кабинетного исследования. Все архитектурные решения ниже — рекомендации, пока не утверждены. Нагрузочные эксперименты, интервью, установка зависимостей и проверка совместимости конкретных версий не выполнялись.

## 1. Вывод

Для портфолио-продукта одной компании предлагается модульный монолит Laravel, React SPA, PostgreSQL, очередь Redis и изолированные обработчики файлов. Это покрывает обязательную модульность и позволяет продемонстрировать реальную надёжность конвейера. Отдельные контейнеры worker/OCR не превращают приложение автоматически в микросервисную архитектуру.

Самые сложные части проекта: согласованность доступа и поиска, повторная обработка без дублей, публикация версий при сбоях, безопасная работа с недоверенными файлами и измеримое качество распознавания. Они должны быть в ТЗ до реализации.

## 2. Альтернативы и продуктовый ориентир

| Альтернатива | Подтверждённое наблюдение | Вывод для проекта |
|---|---|---|
| Paperless-ngx | Есть глобальные и объектные права, поиск по содержимому с оценкой релевантности [S01] | OCR и поиск сами по себе не уникальны; отдельно продумать права и объяснимость результатов |
| Docspell | Документированы OCR, поиск на Solr/PostgreSQL, OIDC и IMAP; в списке возможностей указано отсутствие тонкого управления правами [S02] | Полезный ориентир обработки; предметная ACL может быть сильным демонстрационным сценарием |
| Общая папка/ручной архив | Рабочая гипотеза текущего процесса, интервью не проводились | Проверять выигрыш по времени нахождения актуальной версии |

Не утверждаем отсутствие функций у конкурента только потому, что они не найдены на выбранной странице. Цены, доли рынка и коммерческое преимущество не исследованы. Для учебной цели важнее воспроизводимая демонстрация, чем вымышленная бизнес-модель.

## 3. Модульность и границы

| Вариант | Плюсы | Издержки | Рекомендация |
|---|---|---|---|
| Модульный монолит + workers | Единые транзакции метаданных/ACL/аудита, один release, проще отладка | Границы модулей нужно проверять; общий цикл выпуска | Основной кандидат |
| Микросервисы документов/ACL/поиска | Независимый выпуск и масштабирование | Сетевые сбои, распределённая согласованность, больше CI и инфраструктуры | Только при отдельной учебной цели или доказанной необходимости |

Модули: Identity & Access; Documents & Versions; Processing; Search; Entities; Comments; Audit; Integrations. Каждый владеет своей логикой и изменениями данных. Внешние сервисы доступны через адаптеры. Не добавлять repository над каждым Eloquent CRUD только ради шаблона.

## 4. Поиск: PostgreSQL против OpenSearch

PostgreSQL поддерживает полнотекстовые запросы, веса, ранжирование и фрагменты [S03]. Преимущество для первой версии — ACL и поиск можно проверять в одном SQL-запросе без асинхронной копии прав.

OpenSearch предоставляет отдельную поисковую инфраструктуру и DLS; DLS ограничивает чтение, но не заменяет контроль операций записи [S04]. Выбор этого варианта потребует отдельно спроектировать обновление индекса и мгновенное прекращение доступа после отзыва ACL.

| Критерий | PostgreSQL FTS | OpenSearch |
|---|---|---|
| Эксплуатация | Одна основная БД | Дополнительный сервис и восстановление индекса |
| Права | JOIN/EXISTS по актуальной ACL | Согласованность ACL с индексом требует протокола |
| Ранжирование | ts_rank/ts_rank_cd, веса | Отдельно исследовать настройки анализаторов и ранжирования |
| Длинные документы | Нужна нарезка текста | Также нужна модель документа/фрагмента и тесты |
| Итог | Предпочтительный baseline для одной компании | Кандидат при требованиях, не проходящих baseline |

У PostgreSQL есть ограничение tsvector менее 1 МБ и ограничение позиций [S05]. Поэтому индексировать большой файл одной записью без лимитов нельзя. Предложение: сегменты с порядком и версией документа, объединение совпадений по документу, ограниченная генерация фрагментов. Семантика фразы через границу сегмента должна быть задана; возможны перекрытия сегментов.

Предлагаемые правила: название имеет больший вес, чем основной текст; точные идентификаторы ищутся отдельно от морфологии; сортировка при одинаковом score стабильна; на странице один результат на документ. RU/EN, дефисы, номера, стоп-слова, сканы с OCR-ошибками и очень длинные документы входят в тестовый корпус. Это решения проекта, не гарантия качества по документации.

Нельзя сначала выдать общие total/facets/snippets, а затем скрыть запрещённые карточки. Все производные результаты вычисляются по доступному набору. При смене пользователя очищается клиентский кэш. Кэш поиска на первом этапе можно не вводить; справочники и безопасные метаданные кэшировать проще.

## 5. Распознавание и сущности

Apache Tika документирует интеграцию с Tesseract и выбор языка OCR [S06]. Это кандидат для извлечения текста, а не доказательство качества на нашем корпусе. Примеры на странице включают старые версии; команды установки оттуда нельзя переносить без актуализации.

Предлагаемая стратегия: извлекать встроенный текст; для страниц без пригодного текста запускать OCR. Смешанные PDF проверять постранично. Оригинал неизменяем, результаты обработки — производные артефакты. DOCX-извлечение текста и визуальный preview — разные функции; при необходимости PDF-preview потребуется отдельно исследовать конвертер и его ограничения.

Для сущностей сравнить локальную NER-модель с облачным API. spaCy имеет русские модели, но их заявленный жанр — новости [S07]; качество на договорах и инструкциях не подтверждено. Локальная обработка снижает передачу данных и стоимость запросов, но добавляет Python runtime. Облачная обработка требует бюджета, определения передаваемых данных, таймаутов и лимитов.

Хранить тип, исходное значение, нормализованное значение, источник/фрагмент, версию обработчика и статус проверки человеком. Не показывать выдуманный процент уверенности, если используемый метод не выдаёт калиброванную оценку. Регулярные выражения годятся для некоторых структурированных полей, но не заменяют распознавание людей и организаций.

Проверка качества: размеченный набор разрешённых/синтетических файлов; отдельные метрики OCR и precision/recall по типам сущностей; результаты отдельно по языкам и форматам. Порог приёмки устанавливается после согласования корпуса, не берётся из рекламных цифр библиотеки.

## 6. Конвейер и жизненный цикл

Предлагаемые состояния версии: uploaded → quarantined → scanning → extracting → recognizing → indexing → ready. Дополнительно failed, rejected, cancelled. OCR может быть пропущен для пригодного встроенного текста. NER может иметь отдельный статус и не блокировать доступный текстовый поиск — это нужно согласовать.

Laravel поддерживает очереди Redis и другие драйверы; доступны retries и failed jobs [S08]. Эти механизмы не гарантируют выполнение ровно один раз.

Обязательная проектная семантика:

- Задания идентифицируются version_id + stage + processor_version; повтор не создаёт новый документ или дубли сущностей.
- Запись версии и намерения запустить обработку согласованы через transactional outbox; afterCommit само по себе не закрывает окно сбоя между БД и брокером.
- На этапах заданы timeout, число попыток, backoff и ручной retry с правами и аудитом.
- Результат старого задания не заменяет более новую опубликованную версию.
- Ошибка новой версии не скрывает последнюю успешно обработанную.
- Удаление и отмена проверяются перед публикацией результата; запоздалый worker не воскрешает файл.
- Отдельные очереди тяжёлого OCR и коротких задач не позволяют большому PDF заблокировать всё приложение.
- Периодическая сверка находит зависшие задания, orphan-объекты и неопубликованные outbox-записи.

Очередь и вытесняемый кэш желательно разделять по экземплярам Redis/политикам хранения: потеря кэша и потеря задания имеют разные последствия. PostgreSQL остаётся источником состояния обработки.

## 7. Доступ, файлы и аудит

Sanctum описывает cookie-session аутентификацию собственной SPA [S09]. Предлагается общий origin через reverse proxy, HttpOnly session cookies и CSRF-защита. Не хранить долгоживущий bearer token в Zustand/localStorage.

Роль определяет допустимые действия, ACL — доступ к конкретному документу. Сервер проверяет оба условия на API, preview, download, версии, комментарии и результаты поиска. Права на документ не выводятся из знания его UUID. Прямые ссылки на объекты не должны становиться постоянным обходом проверки; короткие подписанные ссылки всё равно имеют окно действия после отзыва, которое нужно явно принять либо использовать авторизованный proxy.

OWASP рекомендует проверять разрешённые типы, ограничивать размеры, контролировать имена и размещение, применять многоуровневую защиту загрузки [S10]. Для проекта: карантин, антивирус, лимиты распакованного DOCX и числа страниц, изолированный процесс с ограничениями CPU/RAM/времени, запрет произвольных сетевых обращений парсера. Расширения и Content-Type недостаточно.

HTML из документа, комментария или поискового highlight не вставляется как доверенный HTML. Preview не исполняет активное содержимое. Логи не содержат текст документов, пароли, токены и полные поисковые запросы по умолчанию.

Аудит отдельно от диагностических логов: actor, action, resource/version, outcome, время UTC, request_id, разрешённые изменения полей. Запись только на добавление через приложение не означает криптографическую неизменяемость от администратора БД; такую гарантию не заявлять без отдельного решения.

## 8. Клиент и OpenAPI

Pages-first относится к FSD 2.1: код, используемый только страницей, остаётся внутри неё [S11]. Предлагаем ограниченный набор app/pages/features/shared. Это выбранное подмножество слоёв, а не утверждение, что FSD запрещает остальные.

React + TypeScript + shadcn/ui заданы владельцем. Zustand — локальное состояние интерфейса; TanStack Query — загрузка, обновление и инвалидирование серверных данных. Поисковый запрос/фильтры/сортировка — в URL. Данные документов не дублировать в двух глобальных хранилищах.

Scramble генерирует OpenAPI из Laravel [S12]. openapi-typescript превращает OpenAPI 3.0/3.1 в TS-типы [S13]; openapi-react-query связывает типизированный клиент с TanStack Query [S14]. Это основной кандидат. Версии и обработку Sanctum/CSRF, multipart-upload, download и ошибок нужно проверить отдельным экспериментом после согласования реализации.

Контракт сначала согласуется как дизайн; экспорт из кода должен проходить проверку против ожидаемого контракта. Нельзя поддерживать вручную два независимых источника истины. CI проверяет схему, её изменения, генерацию типов и отсутствие необъяснимого diff. Типы TypeScript не валидируют ответ сервера в runtime — нужны контрактные/API-проверки.

## 9. Интеграции

Обновление: владелец подтвердил бесплатный локальный запуск. Облачные варианты в таблице ниже сняты с обязательного scope; актуальное предложение — раздел 13. Формальное значение «внешние интеграции» ещё не уточнено. Ранее рассмотренные кандидаты:

| Возможность | Реальная ценность | Что проверить до выбора |
|---|---|---|
| S3-совместимое внешнее хранилище | Оригиналы и производные файлы | Цена, регион, private buckets, presigned URL, backup |
| Транзакционная почта | Приглашения и восстановление доступа | Провайдер, домен, sandbox, повторная доставка |
| Google Drive import либо OIDC SSO | Импорт рабочих документов либо корпоративный вход | OAuth scopes, отзыв доступа, лимиты, демонстрационный аккаунт |

Это кандидаты, а не подтверждённая совместимость. PostgreSQL, Redis и локальный OCR не считать автоматически тремя внешними интеграциями. Для локального запуска могут использоваться эмуляторы/локальные адаптеры, но приёмка внешней интеграции должна отдельно показывать реальный обмен с выбранным сервисом. Подключённые инструменты этого чата не являются интеграциями разрабатываемого продукта.

## 10. UX-направление

Главные экраны: поиск/библиотека; загрузка и обработка; документ с preview, метаданными, сущностями, версиями и комментариями; управление доступом; пользователи; аудит. Очередь обработки показывает этап и понятную ошибку с доступным действием, а не только бесконечный spinner.

Результат поиска: название, тип, совпавший фрагмент, актуальная версия и дата. Метки подтверждения человеком отделены от автоматических предположений. Empty, loading, failed, denied, offline и частично обработанный документ проектируются отдельно. Основные действия доступны с клавиатуры; цвет не единственный носитель статуса. Финальная палитра и контраст проверяются на макетах.

## 11. Доставка и доказательства качества

Compose: web/reverse proxy, api, worker, scheduler, PostgreSQL, Redis, обработчики и хранилище по выбранной схеме. Мониторинг и локальная почта могут быть профилями. depends_on не заменяет готовность сервиса; Docker документирует условия запуска и healthcheck [S15]. Workers должны переживать временное отсутствие зависимостей и после старта.

Unit: вычисление прав, переходы состояний, нормализация. Integration: реальная БД, очередь, object storage и индексация. API: контракты, session/CSRF, недопустимые входы, матрица ролей. E2E: загрузка → ready → поиск → версия → комментарий → отзыв доступа. Отдельно: повтор задания, остановка worker, недоступный storage, конкурентные версии, удаление во время OCR.

CI по PR: линтеры/форматирование, typecheck, тесты, проверка OpenAPI, сборка клиента и Docker-образов, сканирование зависимостей/образов. После merge — публикация неизменяемого образа, миграции, deploy, smoke и проверяемый rollback. Конкретная CI-платформа и сервер пока не выбраны. Настройка workflow без успешного развёртывания не считается завершённым CD.

Наблюдаемость: структурированные логи с request/job ID; latency/error rate API, глубина/возраст очереди, длительность этапов, ошибки OCR, доля обработанных документов; liveness и readiness с разными смыслами. Метрики не должны содержать doc_id или user_id как высококардинальные labels.

Backup включает БД и файлы; восстановление поискового индекса должно быть воспроизводимо. Значения RPO/RTO, объём корпуса, p95 и аппаратный профиль ещё не согласованы. Замерять скорость без размера файлов, OCR-нагрузки и конфигурации машины недостаточно.

## 12. Следующие проверки до реализации

1. Проверить сценарии, лимиты и бесплатную доступность выбранных Яндекс Диска и Облака Mail; локальные сервисы проверить на совместимость и ресурсы.
2. Согласовать тестовый корпус, объёмы и критерии качества; не использовать личные документы без разрешения.
3. Закрыть ACL, наследование, версии, удаление и правила поиска.
4. Зафиксировать версии и лицензии зависимостей после проверки совместимости; не использовать latest в воспроизводимом окружении.
5. Оформить ADR для поиска, обработки, авторизации и генерации контрактов.
6. Составить FR/NFR, матрицу трассируемости, ТЗ и backlog; получить согласование перед кодом.

## 13. Бесплатная локальная конфигурация — уточнение 2026-10-31

Требование владельца: полностью бесплатный локальный запуск. Рекомендация — отсутствие облачных ключей, подписок и внешней передачи документов в обязательном пользовательском сценарии. Интернет для первичной загрузки зависимостей и обновлений не равнозначен облачной обработке; отдельное требование air-gap не установлено.

| Сервис-кандидат | Интерфейс и назначение | Проверка интеграции |
|---|---|---|
| Apache Tika + Tesseract | HTTP; извлечение текста и OCR | Текстовый PDF, скан RU/EN, повреждённый файл, timeout |
| Gotenberg | HTTP; DOCX → PDF для preview | Корректный preview, кириллица/шрифты, ошибка конвертации |
| ClamAV | Протокол clamd; проверка до парсинга | Безопасный тестовый образец EICAR, clean, недоступность сканера |

Tika имеет официальный проект Docker-образов [S16]. Gotenberg предоставляет Docker API конвертации офисных документов в PDF [S17]. ClamAV предоставляет отдельный daemon и протокол [S18]. Это три содержательные интеграции со сторонними продуктами, а не подсчёт контейнеров БД и очереди. Впоследствии владелец добавил два облачных коннектора; актуальное решение — раздел 14.

Mailpit принимает SMTP и позволяет просмотреть письма локально [S19]. Его использовать для демонстрации приглашений и восстановления пароля; не заявлять доставку на реальные адреса. Хранение оригиналов и производных файлов можно начать с приватного volume через Laravel storage adapter. Для сущностей остаётся локальный NLP; платные LLM API не требуются. Keycloak исследован как вариант локального OIDC [S21], но добавлять его только ради количества интеграций не рекомендуется.

Для ClamAV нужны предварительно загруженные базы; FreshClam обновляет их через сеть [S20]. Без баз сканирование не объявляется успешным; документ остаётся в карантине. Возраст баз отображается администратору. OCR-модели и шрифты необходимо включить в воспроизводимое окружение. Образы и модели фиксировать по версиям после проверки совместимости.

План проверки локальности: после первичной подготовки отключить исходящий интернет и пройти upload → scan → extract/OCR → entities → search → preview → comment/version, а также локальные письма. Это будущая проверка, сейчас не выполнена. Учитывать оперативную память всех обработчиков; минимальные характеристики назвать после измерения, а не по отдельному сервису.

## 14. Яндекс Диск и Облако Mail — решение владельца 2026-10-31

Включить оба коннектора в поставку вместе с тремя локальными интеграциями. Они не являются обязательной зависимостью локального запуска. Предыдущее исключение облачных вариантов из обязательного scope означает отсутствие обязательной облачной зависимости, а не запрет реализовать опциональное подключение.

| Провайдер | Подтверждённый способ | Ограничения исследования |
|---|---|---|
| Яндекс Диск | Официальный REST API, OAuth-токен [S22] | Нужны проверка минимальных scopes чтения/записи для импорта/экспорта, регистрации приложения, локального redirect URI, квот и реальный тест |
| Облако Mail | Официально описанный WebDAV, https://webdav.cloud.mail.ru, пароль внешнего приложения [S23] | Не обещаем OAuth/REST API без документации; бесплатный аккаунт, листинг и скачивание требуют реального теста |

Официальная инструкция Mail требует пароль приложения вместо основного пароля аккаунта. «Облако Mail» и VK Cloud Object Storage — разные продукты; исследуется пользовательское Облако Mail. Не использовать недокументированные внутренние API сайта или автоматизацию пользовательского входа.

Предлагаемый общий интерфейс адаптера: connect/checkConnection, listDirectory с курсором/постраничностью по возможностям провайдера, readMetadata, downloadStream, disconnect. Для WebDAV использовать ограниченный обход PROPFIND Depth:1, а не неограниченный рекурсивный листинг. Конкретный протокол ответа и возможности ETag предстоит проверить, не предполагать их одинаковыми у провайдеров.

Предлагаемые сценарии и критерии:

- Подключения принадлежат конкретному пользователю; другой сотрудник не может просматривать облако через его connection_id.
- Пользователь выбирает файлы и запускает импорт. Фоновые задания показывают прогресс и итог по каждому файлу.
- Размер и разрешённый формат проверяются по фактически полученным данным; скачивание потоковое с жёстким пределом, а не полной загрузкой в память.
- Импорт сохраняет provider, connection_id, remote identifier/path и доступный маркер версии; после скачивания вычисляется локальная контрольная сумма. Повтор одного задания не создаёт дубль. Повторный пользовательский импорт и переименования источника требуют отдельного правила.
- Скачивание даёт локальную копию. Изменение или удаление источника не изменяет локальный архив автоматически; UI это явно сообщает.
- ACL источника не переносится. Начальная видимость — только импортировавшему сотруднику, затем штатное предоставление доступа; политика администратора остаётся общим открытым решением.
- Импорт проходит антивирус, извлечение/OCR, сущности и поиск; происхождение доступно в карточке и аудите.
- Нет сети, отказ авторизации, удалённый файл, rate limit и timeout имеют различимые ошибки. Retry ограничен; при отзыве доступа автоматические попытки прекращаются до переподключения.
- Секреты зашифрованы на сервере; ключ вне репозитория/БД, не попадает в образы. Пароли и токены не передаются клиенту повторно и не пишутся в job payload/логи.
- Разрешены только адреса выбранного провайдера; редиректы и download URL проверяются, credentials не пересылаются произвольному хосту. XML WebDAV разбирается без внешних сущностей.
- Disconnect удаляет локальные credentials и отменяет ожидающие операции; уже импортированные документы сохраняются. Удаление локального секрета не означает отзыв токена у провайдера: способ удалённого отзыва описать отдельно.

Обновление: пользователь подтвердил и импорт, и экспорт для обоих провайдеров. Автоматическая двусторонняя синхронизация не запрошена. Данные из локального архива в облако без отдельного действия не отправляются.

План тестирования: unit/contract через фиксированные обезличенные ответы; integration через контролируемые тестовые сервисы; отдельный ручной/live smoke для каждого реального аккаунта с тестовым файлом. В CI секреты реальных аккаунтов не нужны для обычного PR; live-проверки выполняются отдельно. Сейчас подключения не создавались, реальные документы не читались, доступность на бесплатном аккаунте не проверена.

- S23: https://help.mail.ru/cloud/desktop/webdav/ (на странице указано обновление 2026-03-03).


## 15. Исследование экспорта — уточнение 2026-10-31

Экспорт подтверждён владельцем. Расширить адаптер операциями uploadStream и проверки результата; конкретные методы провайдеров и условные операции записи проверить перед реализацией. Яндекс официально предоставляет API сохранения файлов [S22]; Mail документирует WebDAV и загрузку [S23]. Поддержка атомарного create-if-absent, checksum и условного MOVE у Mail пока не проверена. Предварительный листинг сам по себе не устраняет гонку имён.

Предлагаемая надёжность: transfer_id, user_id, connection_id, document_version_id, destination, planned_remote_name, status, attempts, provider_result и timestamps. Назначение и версия неизменны для повтора одной операции. В имя можно включить короткий уникальный ID передачи, чтобы снизить конфликты; гарантии неперезаписи требуют проверки протокола. Если провайдер не обеспечивает необходимую семантику, нельзя обещать её только на основании локального mutex.

Статусы: queued, running, succeeded, failed, cancelled, outcome_unknown. После разрыва соединения проверить наличие и соответствие результата доступными метаданными/хешем; если достоверная проверка невозможна, показать неопределённый результат, не отправлять слепо новый файл. ETag не считать автоматически хешем содержимого. Успех означает подтверждение завершения провайдером, а не просто отправку задания в очередь.

Право export проверяется отдельно от view при постановке и перед передачей байтов; точная ролевая матрица ещё не утверждена. Отзыв доступа во время передачи обрабатывается best effort: отменить можно только оставшуюся работу, уже переданные байты невозможно гарантированно вернуть. Отключение интеграции запрещает новые операции и отменяет ожидающие; удаление уже созданных облачных копий не выполняется автоматически.

Проверки: одинаковые имена; нехватка квоты; write permission denied; отзыв credentials; повтор job; новая локальная версия после постановки экспорта; сетевой разрыв до/после записи; пакет с частичным успехом; пустой/большой файл; кириллица в имени; попытка экспортировать запрещённый документ через чужое connection_id. Реальные аккаунты и тарифные ограничения ещё не проверены.
