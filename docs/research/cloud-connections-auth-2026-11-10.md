# Подключение Яндекс Диска и Облака Mail без ручного копирования секретов

Дата проверки: 10 ноября 2026 года. Объект: личные аккаунты пользователей Modern Tech, а не сервисные аккаунты Yandex Cloud или объектное хранилище VK Cloud.

## Вывод

Для Яндекс Диска подтверждён официальный OAuth-сценарий: пользователь нажимает кнопку, входит на стороне Яндекса и разрешает доступ, а сервер приложения получает токены. Копирование токена пользователем можно убрать. Для Облака Mail подтверждён WebDAV с отдельным паролем приложения; общедоступный OAuth-сценарий именно для файлов потребительского Облака в проверенных документах не подтверждён. Эти подключения не следует представлять пользователю как два одинаковых способа входа. [Доступ к API Диска](https://yandex.com/dev/disk-api/doc/en/concepts/quickstart), [OAuth-код Яндекса](https://yandex.ru/dev/id/doc/ru/codes/code-url), [WebDAV Облака Mail](https://help.mail.ru/cloud/desktop/webdav/).

## Яндекс Диск: что подтверждено

### Приложение регистрирует администратор сервиса

В нынешнем Яндекс OAuth есть два типа приложений. Тип «Для авторизации пользователей» поддерживает доступ к данным пользователей и настраиваемые Redirect URI. Тип «Для доступа к API или отладки» описан как работающий с данными разработчика; его Redirect URI изменить нельзя, используется `https://oauth.yandex.ru/verification_code`. Для пользовательского подключения Modern Tech нужно регистрировать первый тип, а не отправлять каждого сотрудника создавать своё отладочное приложение. Тип после создания изменить нельзя. Для приложений авторизации действует ограничение до трёх групп разрешений. [Типы приложений](https://yandex.ru/dev/id/doc/ru/register-client), [регистрация пользовательского приложения](https://yandex.ru/dev/id/doc/ru/register-auth), [ограничения отладочного приложения](https://yandex.ru/dev/id/doc/ru/register-api).

Для пользовательского приложения задаются название, иконка, контактная почта, веб-платформа и callback. В зарегистрированном и фактическом Redirect URI должны совпадать схема, хост, порт и путь. Яндекс предупреждает, что пользователи неверифицированного сервиса увидят предупреждение перед выдачей доступа. [Регистрация приложения для авторизации](https://yandex.ru/dev/id/doc/ru/register-auth).

**Локальный callback остаётся проверкой перед реализацией.** Из прочитанных документов Яндекс ID нельзя уверенно обещать, что конкретный `http://localhost:8088/...` будет принят при регистрации. В примерах OAuth есть HTTP-перенаправления, но это не отдельная гарантия поддержки локального callback. Проверить URL в реальном кабинете приложения; если он не принимается, использовать HTTPS-окружение разработки. Правила localhost из Yandex Cloud Identity Hub к Яндекс ID автоматически не переносятся. [Правила Redirect URI](https://yandex.ru/dev/id/doc/ru/register-auth), [параметр redirect_uri](https://yandex.ru/dev/id/doc/ru/codes/code-url).

### Получение и обновление токена

Поддерживается Authorization Code Flow: переход на `https://oauth.yandex.ru/authorize` с `response_type=code`, возврат кода в callback и серверный `POST /token`. Код действует 10 минут. Документированы `state`, PKCE с предпочтительным `S256`, передача `code_verifier` при обмене, а также `force_confirm` для повторного запроса согласия. Яндекс рекомендует не хранить токены в браузере и открытых конфигурациях. [Получение кода из URL](https://yandex.ru/dev/id/doc/ru/codes/code-url).

Документирован обмен `refresh_token` на OAuth-токен через `grant_type=refresh_token`; ответ содержит токены и `expires_in`. Новый основной токен при обновлении может совпасть с предыдущим. Следовательно, нужны хранение фактического срока действия и обработка ответа обновления, а не предположение о вечном токене. [Обновление токена](https://yandex.ru/dev/id/doc/ru/tokens/refresh-client).

### Права на файлы

API Диска использует отдельные разрешения: `cloud_api:disk.read` — чтение всего Диска, `cloud_api:disk.write` — запись, `cloud_api:disk.app_folder` — папка приложения, `cloud_api:disk.info` — сведения о Диске. API получает токен через заголовок `Authorization: OAuth ...`; загрузка и скачивание используют выдаваемые API адреса файловых сервисов. [Официальный старт API](https://yandex.com/dev/disk-api/doc/en/concepts/quickstart).

Выбор прав — продуктовая развилка. Для импорта произвольных существующих файлов нужна возможность их читать. Ограничение папкой приложения снижает объём выдаваемого доступа, но меняет сценарий: пользователь не сможет просто выбрать любой свой файл за её пределами. Не запрашивать запись лишь ради импорта; экспорт требует отдельного обоснования прав. Это рекомендации по минимизации доступа, а не результат проверки настоящего аккаунта.

## Облако Mail: что подтверждено и что нет

### Подтверждённый путь — WebDAV

Mail документирует сервер `https://webdav.cloud.mail.ru` и вход по адресу почты и паролю внешнего приложения. С 1 января 2022 года обычный пароль аккаунта для WebDAV не подходит. Это требование самого провайдера, а не лишнее поле в Modern Tech. Страница WebDAV обновлена 3 марта 2026 года. [Официальная инструкция WebDAV](https://help.mail.ru/cloud/desktop/webdav/).

В актуальной инструкции создания пароля нужно выбрать тип «Полный доступ к Облаку», а не полный доступ ко всей Почте, Облаку и Календарю. Для создания специального пароля требуется привязанный телефон. Пароль имеет задаваемое пользователем название и может быть удалён отдельно; забытый пароль предлагается создать заново. [Пароли внешних приложений](https://help.mail.ru/mail/login/mailer/).

### Не приравнивать вход через Mail/VK ID к доступу к файлам

Официальный раздел OAuth Mail описывает авторизацию пользователя на стороннем сервисе. Официальное описание компонентов Облака отдельно перечисляет API веб-версии, API собственных приложений и WebDAV. Эти документы не подтверждают, что произвольное зарегистрированное стороннее OAuth-приложение получает публичные scopes на чтение/запись файлов Облака. [OAuth Mail](https://help.mail.ru/developers/oauth/), [описание компонентов Облака, PDF](https://cloud.mail.ru/LA/about_cloud.pdf).

**Результат исследования:** открытая поддерживаемая связка «своё OAuth-приложение → согласие пользователя → REST API файлов потребительского Облака Mail» в проверенных официальных источниках не установлена. Это не утверждение, что такой доступ нигде не существует. Для обещания входа одной кнопкой нужно получить у Mail документацию, scopes и условия подключения партнёра. Использование приватных API, cookie-сессий сайта или идентификатора чужого официального клиента не является подтверждённым поддерживаемым решением.

### Платность не установлена

На прочитанных актуальных страницах WebDAV и создания паролей не указано, что именно WebDAV Облака обязательно требует платной подписки. Поэтому нельзя писать в интерфейсе безусловное «только платный тариф». Это также не доказательство бесплатной доступности для любого аккаунта: доступность и ошибки следует проверить на реальном аккаунте. Условия почтовых клиентов и подписок нельзя автоматически переносить на файловый WebDAV. [WebDAV](https://help.mail.ru/cloud/desktop/webdav/), [специальные пароли](https://help.mail.ru/mail/login/mailer/).

## Предлагаемый пользовательский сценарий

Следующие пункты — рекомендации для Modern Tech на основе установленных возможностей; это не уже реализованное поведение.

| Провайдер | Основное действие | Что пользователь вводит в Modern Tech | Однократная настройка владельцем приложения |
|---|---|---|---|
| Яндекс Диск | «Подключить Яндекс Диск» → страница согласия Яндекса → возврат | Ничего из токенов и паролей | OAuth-приложение, Client ID/secret, разрешения и callback |
| Облако Mail | Встроенная пошаговая инструкция → «Проверить и подключить» | Адрес облачного аккаунта и отдельный пароль приложения один раз | Проверенный WebDAV-адаптер; сервер уже известен приложению |

Не делать модальное окно обязательной частью подключения: шаги Mail и результат проверки можно раскрыть в карточке провайдера. Дать прямую ссылку на официальную инструкцию, указать нужный тип пароля, возможность показать/скрыть введённое значение и понятное действие замены пароля. Не просить пользователя задавать адрес WebDAV, endpoint API, Client ID или secret своего приложения. Обычный пароль от почты не предлагать.

После подключения показывать провайдера, понятное имя облачного аккаунта, дату последней успешной проверки, разрешённые действия и «Переподключить»/«Отключить». Состояние «Подключено» должно означать успешный запрос к хранилищу, а не только наличие строки с секретом в БД. Для Mail можно осторожно предложить почту пользователя как редактируемое предположение; учётная запись Modern Tech не доказывает, какой облачный аккаунт он хочет подключить.

Для Яндекса рекомендован серверный callback с одноразовым `state`, привязанным к текущему вошедшему пользователю, PKCE S256 и фиксированным допустимым адресом возврата. Токены шифровать на сервере, хранить срок действия и выданные scopes, обновлять без ручного ввода и показывать необходимость повторного согласия после отзыва. Не включать токены или callback-коды в клиентский URL приложения, логи и сообщения ошибок. Одновременно учитывать, что refresh не заменяет повторное согласие при недостаточных правах.

## Что нужно проверить настоящим сценарием

1. Зарегистрировать приложение Яндекса правильного типа и проверить принятие callback для локального стенда; согласие, отказ, выбор другого аккаунта, протухший/повторный callback.
2. Получить реальные токены, проверить чтение списка файлов, импорт и экспорт в выбранных правах; затем отзыв доступа, обновление и повторное подключение.
3. На отдельном тестовом аккаунте Mail проверить пароль с доступом только к Облаку, корень WebDAV, папки, кириллические имена, импорт, экспорт без перезаписи и отзыв пароля.
4. До проверки не считать наличие UI и успешные тесты с заглушками доказательством рабочего подключения к провайдеру. Поддерживаемый OAuth для файлов Mail, допустимость локального HTTP callback и требования тарифа остаются отмеченными выше границами подтверждения.

## Аудит текущей реализации проекта

### Что уже есть

- Форма требует имя подключения и пользовательский токен для Яндекса либо email и пароль для Mail. Это ручное подключение, а не OAuth redirect-сценарий. Экспорт дополнительно требует вручную указать путь назначения. [IntegrationsPage](../../frontend/src/pages/integrations/ui/IntegrationsPage.tsx), [CloudExport](../../frontend/src/features/cloud-export/index.tsx).
- Яндекс уже работает через REST API и заголовок OAuth. Для Mail реализован официальный WebDAV: `PROPFIND` с `Depth: 1`, загрузка через `GET`, выгрузка через `PUT` с `If-None-Match: *`. Это пригодная основа: менять транспорт Яндекса ради автоматического получения токена не требуется. [YandexDisk](../../backend/app/Modules/Integrations/Services/YandexDisk.php), [MailCloud](../../backend/app/Modules/Integrations/Services/MailCloud.php).
- Секреты скрыты из сериализации модели и шифруются через `encrypted:array`. При обработке переноса повторно проверяются права, импорт проходит через карантин, а записи в облако не повторяются вслепую. Эти меры стоит сохранить при улучшении авторизации. [CloudConnection](../../backend/app/Modules/Integrations/Models/CloudConnection.php), [ProcessTransfer](../../backend/app/Modules/Integrations/Jobs/ProcessTransfer.php).

### Проблемы, влияющие на пользователя

1. **Ложное состояние «Подключено».** `store` проверяет форму и создаёт запись без запроса к провайдеру. Поле `status` по умолчанию равно `connected`. Следовательно, неверный токен или пароль может выглядеть успешным подключением до первой попытки открыть файлы. Нужна проверка доступа перед успешным завершением или отдельное честное состояние «Не проверено». [ConnectionController](../../backend/app/Modules/Integrations/Http/ConnectionController.php), [миграция cloud_connections](../../backend/database/migrations/2026_10_31_000004_create_cloud_transfers.php).
2. **Ошибка не соответствует провайдеру.** При отказе авторизации сообщение в `files` советует отключить подключение и создать его с токеном Яндекса даже для Mail. Статус не переводится в состояние необходимости переподключения; отдельного восстановления доступа нет. Нужны сообщения для каждого провайдера и замена credentials в существующем подключении. [ConnectionController](../../backend/app/Modules/Integrations/Http/ConnectionController.php).
3. **OAuth-цикл пока отсутствует.** Нет маршрутов начала авторизации и callback, нет конфигурации OAuth-приложения Яндекса. Адаптер принимает готовый токен; жизненный цикл `refresh_token`/`expires_at` не реализован. Поэтому интерфейс пока не может убрать копирование токена простым переименованием кнопки. [Маршруты](../../backend/routes/web.php), [services.php](../../backend/config/services.php), [YandexDisk](../../backend/app/Modules/Integrations/Services/YandexDisk.php).
4. **Ограниченный выбор файлов.** Яндекс запрашивает до 1000 элементов без `offset` и интерфейса постраничной загрузки. Ручной путь экспорта создаёт дополнительный источник ошибок. Нужен выбор папки и имени файла, а для больших каталогов — пагинация и понятный переход по папкам. [YandexDisk](../../backend/app/Modules/Integrations/Services/YandexDisk.php), [CloudExport](../../frontend/src/features/cloud-export/index.tsx).
5. **Ошибки фонового переноса недостаточно понятны в интерфейсе.** Следует различать необходимость повторного входа, отсутствие прав на чтение/запись, существующий файл, нехватку места и временный сетевой сбой, сохраняя запрет слепого повтора неидемпотентных записей. [ProcessTransfer](../../backend/app/Modules/Integrations/Jobs/ProcessTransfer.php), [страница подключений](../../frontend/src/pages/integrations/ui/IntegrationsPage.tsx).

### Что фактически проверено

Локальная БД проверена без чтения секретов: есть одно отключённое подключение Яндекса, активных подключений нет. Поэтому реальные вход, список файлов, импорт и экспорт на аккаунтах провайдеров в этой задаче не подтверждены.

**Состояние стенда — отдельное препятствие.** При проверке API, Redis и PostgreSQL работали, но `scheduler`, `worker-transfers`, `worker-processing`, ClamAV, Tika и Gotenberg были остановлены. Диспетчер outbox запускается планировщиком каждые 10 секунд, а `ProcessTransfer` выполняется очередью `transfers`. Даже верные credentials при таком состоянии стенда не обеспечат выполнение переноса. Полный импорт также зависит от обработки, антивируса и подготовки предпросмотра. Это не дефект OAuth. Сервисы намеренно не запускались в рамках анализа: запуск очереди может исполнить ранее ожидавшие операции. [Конфигурация сервисов](../../compose.yaml), [планировщик outbox](../../backend/routes/console.php), [ProcessTransfer](../../backend/app/Modules/Integrations/Jobs/ProcessTransfer.php).

Автоматические проверки:

- `CloudCredentialsTest`: 1 тест прошёл, 3 проверки.
- Фронтенд-тест страницы интеграций: 1 тест прошёл.
- `CloudTransferTest`: 1 тест прошёл, 2 упали до сетевого запроса — тесты создают `new UploadDocument` без обязательного `FileInspector`. Это проблема актуальности тестовых фикстур, а не результат обращения к облакам.

Внешние аккаунты и секреты при анализе не использовались; код приложения не менялся. Успешные тесты с заглушками не являются реальной проверкой провайдеров.

## Порядок улучшений

1. Реализовать серверный OAuth-цикл Яндекса с одноразовой настройкой приложения владельцем Modern Tech, `state`, PKCE, зашифрованными access/refresh-токенами и временем действия. Проверить callback на фактическом окружении.
2. Исправить проверку credentials, состояния подключения и повторное подключение. Актуализировать тесты переноса; затем проверить настоящие аккаунты отдельными безопасными сценариями.
3. Для Mail оставить официальный WebDAV, но сделать короткую встроенную инструкцию с правильным типом пароля, непосредственной проверкой доступа и понятной заменой пароля; без обязательного модального окна.
4. Добавить выбор папки экспорта, пагинацию каталогов и сообщения об ошибках по конкретному действию. Возможный OAuth для файлов Mail исследовать отдельно после получения официального подтверждения от провайдера, не блокируя улучшения подтверждённого пути.
