## 3. Продуктовая гипотеза

Сотрудник находит актуальный документ по словам из его содержимого, даже если файл был сканом и его название неизвестно. Система показывает только разрешённые документы, историю версий и обсуждение. Администратор может установить, кто изменил документ или его доступ.

Это рабочая гипотеза ценности, а не результат интервью. Коммерческая уникальность и рыночный спрос не доказаны и не являются обязательным условием портфолио-проекта.

Предлагаемый демонстрационный сценарий: сотрудник загружает скан → видит этапы обработки → находит документ по фразе внутри → проверяет извлечённую организацию → добавляет комментарий → загружает новую версию → администратор ограничивает доступ → другой сотрудник перестаёт видеть документ во всех каналах.

## 4. Предложения, ещё не утверждённые

- В первой версии одна организация, пользователи по приглашениям, без публичной регистрации, биллинга и межорганизационного обмена.
- Любая тематика; поддерживаемые форматы PDF, DOCX, TXT, PNG, JPEG. PDF может быть текстовым, сканированным или смешанным. Иные форматы не принимаются молча как успешно обработанные.
- Русский и английский текст. Рукописи, распознавание сложных таблиц и математических формул без обещаний качества.
- Сущности: люди, организации, места; email/телефоны/даты отдельными правилами. Предложения можно исправлять и отклонять. ИНН, суммы и реквизиты — возможное расширение, не универсальное свойство каждого документа.
- Поиск только по опубликованной версии по умолчанию; архивные версии доступны отдельно.
- Базовые роли и права утверждены в U-22. Детализация управления доступом и исключения администратора описаны в ACCESS_MODEL.md как предложения.
- Комментарии к документу с указанием версии; без совместного редактирования офисного файла.
- Мягкое удаление с последующей очисткой; срок хранения ещё не установлен.
- Минималистичный интерфейс: нейтральные поверхности, графитовый текст, один синий/индиго акцент. Цвета являются дизайн-предложением, а не исследованным предпочтением пользователей.

## 6. Порядок работы

1. Уточнить ограничения и завершить адресное исследование интеграций.
2. Согласовать границы первой версии и сценарии, включая ошибки и права.
3. Подготовить PRD, формальные FR/NFR, матрицу доступа, модель данных, API и ADR.
4. Собрать ТЗ, экспортировать и проверить фактические 25–30 страниц; Markdown сам по себе не имеет фиксированной пагинации.
5. Провести аудит полноты: каждое требование связано с критериями приёмки и проверками.
6. Согласовать backlog и затем создать tasks.json, схему его проверки и progress.md.
7. Настроить репозиторий, приложения, Compose и CI; разработать сквозной сценарий, затем остальные модули.
8. Проверить тесты, безопасность, восстановление, деплой и демонстрацию.

## 8. Применение шаблона tasks.json

Сохранить category, priority, acceptance_criteria, test_steps, dependencies и status. Добавление requirement_ids, epic_id и validation_evidence предложить при согласовании схемы, не менять её молча.

Ограничения шаблона требуют адаптации: 15–50 задач и каждая до 30 минут могут противоречить объёму полноценной системы. Рекомендация — эпики и небольшие проверяемые задачи без фиктивной гарантии времени. Запрет изменять задачи должен защищать согласованный scope, но допускать явную процедуру изменения требований. Правило done требует фактических результатов проверок; инфраструктурные задачи проверяются соответствующими командами, а не искусственным пользовательским E2E.

## 9. Уточнение: локальный запуск

Бесплатный локальный запуск подтверждён владельцем. Предлагается обычная первоначальная загрузка образов, зависимостей, языковых моделей и антивирусных баз из интернета; дальнейшая работа с документами локальная. Полностью автономная первоначальная установка пока не запрошена. Документы не передаются облачным OCR/LLM.

Кандидаты независимых сторонних сервисов в Compose: Apache Tika/Tesseract (текст и OCR), Gotenberg (PDF-preview офисных файлов), ClamAV (антивирус). Это интеграции по API/протоколу с отдельными продуктами. Владелец дополнительно выбрал Яндекс Диск и Облако Mail (см. раздел 10). Mailpit — локальная проверка приглашений/восстановления, а не доставка в настоящие почтовые ящики. Хранение файлов — закрытый Docker volume с доступом через приложение; S3 пока не обязателен.

Локальность приложения не отменяет PR-review и CI/CD. Платформу репозитория и способ бесплатной демонстрации deploy предстоит выбрать отдельно; платный VPS не требуется.

## 10. Решение: пять интеграций

Владелец согласовал три локальных сервиса и добавил Яндекс Диск и «вк mail диск», интерпретированный как пользовательское Облако Mail, а не инфраструктурный VK Cloud Object Storage.

Облачные коннекторы входят в план реализации, но их активация не обязательна для работы приложения. Без аккаунтов и интернета локальные загрузка, OCR, поиск, версии, комментарии и ACL продолжают работать. Реальная проверка облачных коннекторов требует аккаунтов и подключения к сети; mock-тесты не заменяют такую проверку.

Предлагаемый scope первой версии: подключить личный аккаунт, просмотреть файлы и вручную импортировать выбранные документы в локальный архив. Импорт — создание локальной копии, а не синхронизация. Экспорт впоследствии подтверждён владельцем; автоматическая синхронизация папок и удаление в источнике пока не согласованы. Облачные файлы проходят тот же карантин и конвейер, что обычная загрузка. Облачные права автоматически не переносятся; импорт по умолчанию приватный.

Q-09 закрыт: владелец подтвердил импорт и экспорт для обоих провайдеров. Квоты и доступность протокола на бесплатном аккаунте нужно проверить перед финальной фиксацией критериев приёмки.

## 11. Экспорт — подтверждённый scope и предлагаемые правила

Импорт и экспорт входят в первую версию для обоих провайдеров. Предлагается ручной запуск, одна или несколько выбранных записей, выбор облачной папки и конкретной версии. По умолчанию выгружается оригинал текущей опубликованной версии; комментарии, ACL и аудит не включаются в файл. Экспорт PDF-preview и пакета метаданных отдельно не запрошен.

Предлагаемые критерии: отдельное разрешение export в матрице доступа; повторная проверка перед отправкой worker; фиксация version_id при создании задания; фоновая отправка с итогом по каждому файлу; отсутствие молчаливой перезаписи; по умолчанию новое имя при конфликте. Замена существующего файла не включается без отдельного решения. После timeout с неизвестным результатом сначала сверка, затем повтор; нельзя считать любую ошибку доказательством отсутствия удалённого файла.

Облачная копия имеет права целевой папки, локальные ACL на неё не распространяются. Последующий отзыв доступа в приложении не отзывает уже экспортированную копию. UI сообщает это при выборе назначения. Экспорт не создаёт публичную ссылку автоматически. Автоматическое зеркалирование, удаление в облаке и двусторонняя синхронизация не входят в текущую договорённость.
