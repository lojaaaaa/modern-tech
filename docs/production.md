# Подготовка и запуск production

Площадка и домен выбираются отдельно. Эти действия выполняются на сервере выпуска после настройки HTTPS, резервного копирования и секретов. Автоматический деплой пока не настроен: CI проверяет код и собирает образы без публикации.

## Окружение

Нужны Docker Compose 2.24.4+ (используется `!override`), PostgreSQL, Redis, постоянное хранилище документов и достаточно памяти для ClamAV, Tika, Gotenberg и при необходимости ONLYOFFICE.

На целевом сервере подготовьте `.env` для Compose и `backend/.env` по примерам. Задайте случайные `DB_PASSWORD` и постоянный `APP_KEY`; при обновлении сохраняйте прежний `APP_KEY`, иначе зашифрованные подключения и сессии станут недоступны. Укажите `APP_ENV=production`, `APP_DEBUG=false`, HTTPS в `APP_URL`, домен в `SANCTUM_STATEFUL_DOMAINS`, `SESSION_SECURE_COOKIE=true`, реальные SMTP-настройки и разрешённые адреса OAuth Google.

HTTPS завершается внешним reverse proxy перед портом `127.0.0.1:8089`. Он должен передавать корректные Host и X-Forwarded-Proto и поддерживать WebSocket для ONLYOFFICE. Доступ к PostgreSQL, Redis и внутренним обработчикам наружу не открывается.

## Сборка и первый запуск

Сначала выполните `bash scripts/check-quality.sh` в подготовленном локальном окружении. На сервере используйте один и тот же набор Compose-файлов для всех команд:

```sh
docker compose -f compose.yaml -f compose.production.yaml build api web
docker compose -f compose.yaml -f compose.production.yaml up -d postgres redis-queue redis-cache tika gotenberg clamav api web
docker compose -f compose.yaml -f compose.production.yaml exec -T api php artisan migrate --force
docker compose -f compose.yaml -f compose.production.yaml up -d worker worker-processing worker-transfers scheduler
```

Для совместного редактора добавьте `compose.office.yaml` **перед** `compose.production.yaml`, передайте `.local/office.env` через `--env-file` вместе с `.env` и запустите также `office-documentserver`. Задайте один случайный `OFFICE_JWT_SECRET` для API и редактора и HTTPS-адрес редактора в `OFFICE_PUBLIC_URL`. После изменения окружения пересоздайте также worker и scheduler. Монтируемые тома документов и БД должны сохраняться при обновлении.

Создайте первого администратора через `php artisan app:create-admin <email>`. Пароли демонстрационных пользователей в production не загружаются.

## Проверка выпуска

Проверьте `/health/live` и `/health/ready`, вход и выход, загрузку тестового файла до статуса готовности, поиск, чтение, скачивание, комментарии и права всех трёх ролей. При использовании редактора проверьте сохранение, явное создание версии, одновременную работу двух пользователей и отзыв доступа. Для Google и Mail.ru проверьте импорт и экспорт на тестовых файлах с настоящими подключениями.

Swagger доступен по `/docs/api` на том же домене; отдельный сервер для него не нужен. В production доступ ограничен администратором. Машиночитаемый контракт находится в `contracts/openapi.json`.

Табличный предпросмотр показывает значения XLSX, без пересчёта формул и диаграмм. Нативные Google Docs/Sheets/Slides требуют предварительного экспорта в файловый формат.

## Обновление, резервная копия и откат

Перед миграциями сохраните `pg_dump -Fc`, содержимое тома документов и защищённые конфигурации с `APP_KEY`. Команды резервного копирования выполняйте с тем же набором Compose-файлов, что и запуск. Проверьте восстановление на отдельном стенде; не храните резервные копии в Git.

Зафиксируйте версию исходного кода и теги предыдущих образов. При неудачном выпуске остановите обработчики и верните предыдущие образы. Если миграция несовместима с прежним кодом, восстанавливайте согласованную пару БД и файлов из резервной копии. Не выполняйте `down -v` на рабочем окружении.

Для изолированной проверки production-образов используйте `make staging`: скрипт создаёт отдельные настройки в `.local/staging`, отдельные тома и порт 8089. Это не публикация сайта в интернете. После проверки — `make staging-down`, без удаления томов.
