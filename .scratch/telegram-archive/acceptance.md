# Приёмка Telegram-архива

Основание: SPEC.md, AC-01–AC-16. Границы подтверждены пользователем «да».
Использовать только временный каталог и подставной Telegram. Не запускать
приёмник с реальными .env/data и не отправлять живых уведомлений при разработке.

| Критерий | Проверяемый результат | Граница |
| --- | --- | --- |
| AC-01 | Первая полученная правка не выдумывает before; история явно неполная | Archive + UI |
| AC-02 | Из 20 непрочитанных только 5 показанных становятся read, открытие само не отмечает остальные | HTTP + браузер |
| AC-03 | through_id фиксируется до нового события, новое остаётся unread | Archive + HTTP |
| AC-04 | Доставка notice не меняет read, новое соединение/перезапуск сохраняет read | Archive + receiver |
| AC-05 | Глобальные edits=false сильнее notifications=true диалога, delete остаётся включён | Archive + receiver |
| AC-06 | Повтор update и повтор owner reply не дублируют entries/history/photo/outbox | Archive + receiver |
| AC-07 | Сбой sendMessage сохраняет событие и отложенное задание | receiver |
| AC-08 | Нет файла и ошибка download отличаются, оба не отображаются saved | receiver + UI |
| AC-09 | Алекесй → Алексей; @USERNAME; exact впереди fuzzy; поиск без message text | Archive + UI |
| AC-10 | Новое имя/username/avatar не создаёт диалог; старый entry profile неизменен | Archive + receiver |
| AC-11 | 30 дней/возобновление/legacy restore: raw/nested/background очищены; event/photo остаются | Archive |
| AC-12 | Clear удаляет owned данные/фото/notices; дубликат не воскресает, новый update принимается | Archive + HTTP |
| AC-13 | collecting=false блокирует новые background/event/photo, старые доступны, mute не влияет на сбор | Archive + UI |
| AC-14 | Нет/подмена/чужой/просроченный/future/duplicate-key initData отклоняются для каждого типа операции | HTTP |
| AC-15 | Светлая/тёмная темы, mobile/desktop, safe areas, клавиатура, history return, photo blob auth | браузер |
| AC-16 | Остановка/ошибка приёмника не active; ошибка списка/истории не пустота | receiver + HTTP + браузер |

Дополнительно: первоначальные обычные сообщения не создают событий;
owner edit без notice/unread; обычное фото без owner reply не скачивается;
participant reply не скачивает; notification texts сохраняют полную историю
при разбиении длинных уведомлений и не отправляются исходному собеседнику;
неизвестный инициатор удаления не подменяется исходным автором.

Проверять все случаи через публичные интерфейсы. Доступ к техническому
хранилищу допустим только при проверке миграции/истечения физического хранения,
когда именно это является наблюдаемым требованием, а не заменой поведения API.
Живое получение временных фото и открытие на реальном устройстве Telegram
не доказываются браузером с подставным SDK/API и отражаются как ограничения.

## Исправления после ревью

В ветке `implement/telegram-fixes` устранены три продуктовых находки и
замечание Standards о повторяющихся словарях UI:

- Ручное удаление фиксирует изменения и очищает WAL; занятое чтение,
  помешавшее завершить очистку, возвращает ошибку вместо ложного успеха.
- После истечения фонового текста сохраняются только идентификаторы сообщения
  и признак стороны. Удаление известного собственного сообщения не создаёт
  уведомление или непрочитанное; исходный текст после 30 дней отсутствует.
  Ручное удаление/очистка удаляют и этот признак. Инициатор удаления не выдумывается.
- Повтор загрузки из Mini App отправляет JSON `{}` согласно защищённому API.
  Браузерный сценарий проверяет фактические Content-Type и тело запроса.
- Общие словари медиа и состояний фото используются и в списке, и в записи.

После TDD-исправлений проходят 48 Python-тестов (24 Archive, 15 приёмника,
8 HTTP, 1 конфигурации), `py_compile` и `node --check`. Основной агент повторил
полный `mini_app_states.browser.js` на исправленном UI: новый контроль JSON
запроса сначала воспроизвёл ошибку, затем весь сценарий прошёл с `{}`.
Проверка повтора через настоящий API фиксируется после слияния;
до её результата задачи остаются открытыми.

Открытие в настоящем Telegram через пользовательский HTTPS-адрес, проверка
на физическом устройстве и получение живых временных фото не выполнялись.
Эти ограничения не подменяются результатом подставного SDK. Автоматическое
сохранение временных фото без ответа владельца остаётся отдельным исследованием,
как согласовано в SPEC, и не добавляется к обещанному объёму первой версии.

живых временных фото остаются обозначенными границами проверки.
